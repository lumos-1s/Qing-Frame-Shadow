# 清框影 vs Lumen-win · 技术对比

> 对象：`github.com/bodyzxy/Lumen-win`（v1.0.1，Tauri，2026-11-21 建库，0 star）
> 读的是 `main` 分支源码：Rust 端 180 行 `raw.rs`，前端 3932 行 TS。
> 结论先放这里：**它不是竞品，但它的 RAW 管线比我们诚实，有两条该现在补。**

---

## 一、定位根本不是一回事

|  | Lumen-win | 清框影 |
|---|---|---|
| 干什么 | 只做调色，LR 的轻量替代 | 加框、排版、拼图、切图为主，调色是配菜 |
| 用户 | 想要"打开就调"的人 | 想要"照片变成一张作品"的人 |
| 核心资产 | 调色算法与 Mac 版一一对应 | 91 款边框 + 排版引擎 |

它没有边框、没有拼图、没有 EXIF 签名、没有切图。所以**抢不走你的用户**。

但它有一条你暂时比不了：**它把 RAW 的宽容度真的用上了。**

---

## 二、正面对比

| 维度 | Lumen-win | 清框影 | 谁强 |
|---|---|---|---|
| 技术栈 | Tauri 2 + Rust + WebGL2 + React | Electron 45 + 原生 JS + Canvas2D / WebGL1 | 各有取舍 |
| 安装包 | 预计 10–20MB（未实测，Tauri 典型值） | 117MB 安装包，381MB 解开 | Lumen |
| RAW 解码 | `rawler` 0.8，纯 Rust 进程内，无系统依赖 | `libraw-wasm`，常驻 worker 线程 | 平手 |
| RAW 输出位深 | **线性 f32 sRGB，不压位深** | **8 bit sRGB**（`src/main/raw.js:106` `outputBps: 8`） | **Lumen** |
| 高光恢复 | 线性数据一路到 shader，压高光能找回细节 | `highlight: 0`，曝光完就直接裁掉 | **Lumen** |
| 调色通路 | WebGL2，RGBA16F/32F 全浮点，单 pass 链 | WebGL1 单 pass + 8bit 输出；3D LUT 用 33 张切片横排成 1089×33 条带模拟 | Lumen（精度）/ 我们（兼容） |
| 空间类效果 | `RenderGeometry` 带 `srcRect` / `crop`，可按块渲染，半径按全图尺寸算 | 整张一次渲染 | Lumen（可扩展性） |
| 导出位深 | 8 / 16 bit 可选（`renderer.ts:774` `renderPixels(bits: 8\|16)`） | 8 bit | Lumen |
| 色彩空间 | 只有 sRGB（Mac 版才是 P3） | sRGB / Display P3 / Adobe RGB，真转像素并嵌 ICC | **我们** |
| 中间缓冲 | 多 pass，需要纹理/FBO 池 | 单 pass，一张输出画布全模块复用（`app-color-grade.js:331`） | 平手（各自够用） |
| 工程成熟度 | 两天、无测试、无 issue 模板 | 三个月、几十个测试脚本、`test:gui:chain` | **我们** |
| 版本号 | 1.0.0（虚） | 0.1.29（实） | 见第四节 |

**一句话**：它的**下限**比你高（RAW 那条链路是对的），**上限**比你低（它做不出 91 款边框，也没有 P3 和 ICC）。

## 三、该补的四件事（按性价比排）

> 这一节是当初的判断。**照着做了之后有三处被实测推翻**，逐条结论见第七节，以那里为准。

### P0 · 把 RAW 从 8 位换成 16 位 —— ✅ 已做（全尺寸路径）

`src/main/raw.js:106` 写着 `outputBps: 8`。但 libraw-wasm 的接口是支持的：

```ts
// node_modules/libraw-wasm/dist/index.d.ts
/** Output bits per sample, mapped to `-4` (`8` or `16`). */
outputBps?: number;
```

也就是说，`app-raw.js` 开头那句注释「LibRaw 交出的是 8bit sRGB，显影层再做一遍拿不到额外宽容度」——**这是默认值，不是库的限制。**

改成 16 位之后，同样一张 RAW 从 256 级变成 65536 级，压高光时才有东西可拉。

要注意两件事：

1. **内存翻倍。** `raw.js:198` 那条注释已经记了「libraw 的 wasm 堆只涨不缩，每解一张 24MP 全尺寸大约留下 200MB」。16 位会让这个数字再翻一倍。
   **所以只走全尺寸/导出路径，代理图（长边 1600）继续 8 位。** 拖动滑块时精度不重要，出图时才重要。
2. **像素换装的那几个函数要认 Uint16Array。** `autoGain` / `cropRotate` 大概率按 8 位写的，得改成按位深分支。

### P0 · 打开 LibRaw 的高光恢复 —— ⛔ 试了，撤回（见第七节）

同一处：`highlight: 0`。

LibRaw 的 `-H` 有 0–9 十档，0 是"直接裁掉"，1 以上都是**尝试从相邻通道把过曝的那一两个通道补回来**（因为过曝通常先炸一个通道，另两个还有数据）。这一档对"天空拉回来全是白"的改善，比加任何滑块都直接。

先试 `highlight: 2`。代价是要重新校准 `autoGain` 的基线（恢复模式下整体亮度会变），得拿几张逆光片子对一遍。

### P1 · 中间层改浮点 —— ⛔ 不适用（单 pass，见第七节）

现在 RAW 出来是 8 位，进调色再算一遍，等于每调一次就有一次量化损失。Lumen 全程 RGBA16F，只在最后出图时才降到 8 位。

我们已经有 `OES_texture_float`（`app-color-grade.js:340`），目前只用在阴影通道的两张纹理上。把它扩到主链路，改造成本中等，收益是"连续调十次不脏"。

### P2 · 8192 导出改分块 —— ⛔ 实测不需要（见第七节）

现在导出是一次 `canvas` 画完。8192² × 4 字节 = 268MB，已经贴着浏览器上限；再往上（拼图 + 切图叠加）没有余量。

Lumen 的 `RenderGeometry` 里 `srcRect` / `crop` / `refWidth` / `refHeight` 就是为这个设计的：**只渲染一块，但空间类效果按整张图算**（清晰度半径、暗角中心、颗粒大小都引用 refWidth）。这样分块拼回来不会有接缝。

这份接口定义可以直接照抄，四个字段而已。

> 顺带说清一件事：Lumen 那套纹理池（`acquire(w,h,float32)`）**不是我们现在该抄的**。它是多 pass 管线才需要的东西，我们目前单 pass、一张输出画布全模块复用（`app-color-grade.js:331`），本来就没有反复创建纹理的问题。**等 P1 上了浮点中间层再考虑池化**，那时候才真的会需要。

## 四、不该抄的三件事

**1. 不要为此重写成 Tauri。**
体积从 117MB 降到 15MB，听着诱人。但清框影三个月的分量全压在 Canvas 2D 的排版引擎、91 款边框的绘制代码、Electron IPC 的缓存调度上。换框架等于把这三样重写一遍，换来的只是下载快 30 秒。**不值。**

**2. 不要学它叫 1.0.0。**
它是两天、0 用户、调色还不全，照样 1.0.0。你的 0.1.29 配上"还在修 bug"是人设资产，改了反而不真。

**3. 不要学它只做 sRGB。**
Windows 版它只有 sRGB，你有 P3 和 Adobe RGB 真转换 + ICC 嵌入。**这是你比它强的地方，宣传时该提。**

## 五、可以直接借的六个小技巧

都在 `src-tauri/src/raw.rs`，都是几十行的东西，跟框架无关：

1. **基础曲线用 4096 项 LUT + 线性插值**（`raw.rs:87-100`）
   2400 万像素 × 3 通道逐个算 `powf` 太慢，建表一次、后面查表。我们换装时如果有逐像素幂运算，同样处理。

2. **用 Reiner 曲线做基础提亮**（`raw.rs:42-52`）
   `y = x(1+k)/(1+kx)`，k=0.9。暗部和中间调提亮约 2/3 档，而 1.0 仍然是 1.0——高光不会被推爆。比直接 gamma 温和得多。

3. **半精度 f16 打包传输**（`raw.rs:176`）
   Rust 端 `f16::from_f32(v).to_bits()`，JS 端解成 Float32Array。RAW 数据过大半，IPC 带宽直接减半，肉眼无差。

4. **一次回传多档代理**（`raw.rs:166-180`）
   `[原图宽][原图高][张数]` 之后跟着每档 `[宽][高][数据…]`，一次 IPC 把缩略图、预览、全尺寸都送过去。我们现在是分几次要，每次都要等。

5. **面积平均下采样**（`raw.rs:127-163`）
   按目标像素把源区块求和再除，不是双线性抽点。缩小后不会出现摩尔纹——缩略图墙上一眼能看出区别。

6. **颜色函数在 CPU/GPU 两边用同一份公式**
   `raw.rs` 的 `to_gamma` / `to_linear` 和 `shaders.ts` 的 `toGamma1` / `toLinear1` 是同一组常数。我们 `app-color-grade.js` 有 WebGL 和 Canvas2D 两条路径，注释说"同一套场与系数"——这一点我们早就对了，值得保持。

---

## 六、结论

它的价值不在"能抄什么功能"，在于**它证明了 8 位不是必须的**。

`outputBps: 8` 那行是你自己写的，注释里也承认了「拿不到额外宽容度」。现在知道库支持 16 位，这条限制就不成立了。

**如果只做一件事，做 `highlight: 2`。** 一行改动，逆光片子的观感立刻不一样，而且不碰架构。做完再决定要不要上 16 位。

至于边框——它两天做不出来，那就是你的护城河，安心。

## 七、照做之后：实测记录

第六节那句「如果只做一件事，做 highlight: 2」——**是错的**。真跑了一遍，撤回。

样本：`.tmp/rawspike/user.ARW`（Sony ILCE-6000，6024×4024，ISO 100）与 `sample.ARW`（同机型，ISO 800）。

| 试验 | 数字 | 结论 |
|---|---|---|
| 16 位解码耗时 | 3112ms → 3185ms（全尺寸） | +2.3%，可以接受 |
| 16 位解码内存 | 586MB → 655MB（worker RSS） | +70MB，可以接受 |
| 合成灰阶斜坡（+1.5EV、对比 20） | 8 位链路缺 87/256 级（34%），16 位缺 0 级 | **量化台阶确实被消除了** |
| 真实照片（+2.5EV，1:1 裁切） | 8 位与 16 位：区间都是 42，顶部 77/78，缺级 0/1 | **肉眼分不出** |
| `-H 2` 对分位数的影响 | p99.7 从 182 掉到 104，gain 1.92→3（撞上限） | 全图暗 35%，是回归 |
| `-H 2` 亮度追平后（gain 6.5） | 顶部 2% 的级数 60，`-H 0` 是 59 | **高光没有活过来** |
| 8192² 画布 | 建+画 103ms，读回 105ms，编码 485ms，非空白 | 不需要分块 |
| 12288² 画布 | 228ms / 259ms / 979ms，非空白 | 同上，余量还很大 |
| DHT 去马赛克（userQual 11） | 3467ms → 7635ms，梯度能量 +7.8% | 2.2 倍代价换不明显的锐度，不做 |

### 1. 16 位：做了，但要说清它治的是什么

代码在 `raw-tonemap.js`：`lin16Table` / `buildLut16` / `toBgra16` / `autoGain16`，`cropRotate` / `resizeBox` 按输入缓冲类型自动跟随位深。

策略是**按需**，不是全链路：

- 代理图（1600px，拖动滑块时看的）走 8 位，`halfSize` 已经在用，解码快一倍；
- 全尺寸（停手后补齐、导出前）走 16 位，量化只发生在最后一步 BGRA。

实测诚实结论：**在这两张样本上看不出差别**。原因是最终产物仍是 8 位 JPEG + 8 位 canvas，渲染层还要再套一遍调色，噪声也把台阶抖掉了。

它真正治的是另一种情况：ISO 100 的干净天空、棚拍纯色背景、经过降噪的平滑渐变——那种画面没有噪声帮着抖动，8 位输入在推 2–3 档时会出现横条。合成斜坡上 34% → 0% 就是这件事的量化证明。

同时把全尺寸 JPEG 的质量从 93 提到 95：16 位算出来的渐变，不该在最后一步被 JPEG 重新装回台阶。

### 2. `-H 2`：抄了，然后撤回

失败原因值得记下来，因为它不是一个参数没调好，而是**管线结构决定的**：

`-H > 0` 会让 LibRaw 重新分配量程（把恢复出来的高光也放进输出范围），整张图被压到约 0.57 倍。我们的 `autoGain` 按 99.7% 分位归一到 0.9 线性，理论上能自己补回来——但它被 `[0.5, 3]` 夹住了，需要 6.5，于是全图暗 0.8 档。

把增益手动补到 6.5 让亮度追平后，顶部 2% 的级数是 60，而 `-H 0` 是 59。**没有变多。** 因为 autoGain 会把恢复出来的余量重新归一化掉，高光肩又从固定 knee 起压，一来一回正好抵消。

要让 `-H` 有意义，得先改成「按实际数据范围决定肩位」——那是换一套色调映射，不是改一个参数。留在 `HIGHLIGHT_MODE` 那里的是 `0`，注释里记了这组数字，避免下次有人再试一遍。

### 3. 不适用 / 不需要的三条

- **中间层改浮点（P1）**：我们是单 pass、8 位源纹理进 shader，中间没有任何缓冲。浮点纹理只有在「多 pass + 每 pass 落盘」的管线里才有意义。等哪天 RAW 能直接把线性数据送进 GPU 再说。
- **8192 分块导出（P2）**：实测 8192² 画得动（103ms），12288² 也行（228ms），都不空白。268MB 是内存占用，不是上限。为不存在的瓶颈做分块，等于给每个空间效果都加一层坐标换算的出错机会。
- **纹理池**：第六节已经自我纠正过，单 pass 不需要。

### 4. 第五节的六条小技巧，实际落地情况

| 技巧 | 状态 |
|---|---|
| 4096 项 LUT + 线性插值 | 早就在用（256 项表）。16 位路径扩到 65536 项，直接索引，不需要插值 |
| Reiner 曲线做基础提亮 | **不做**。我们的 autoGain 已经按分位归一，再叠一层 Reiner 等于把亮度管两遍，且会改变所有已存草稿的观感 |
| 半精度 f16 打包 | **不适用**。我们过 IPC 的是 JPEG，不是原始像素 |
| 一次回传多档代理 | **不适用**。代理和全尺寸是两次独立解码（代理用 `halfSize`，快一倍），合并成一次会让导入变慢 |
| 面积平均下采样 | 早就在用（`resizeBox`），缩略图墙上的摩尔纹靠它 |
| CPU/GPU 同一份颜色公式 | 早就对（`toneLinear` 现在被两条位深路径共用，进一步钉死） |

一句话收尾：**能抄的都抄了，抄完发现只有一条真的成立，而且成立的方式和当初想的不一样。**
